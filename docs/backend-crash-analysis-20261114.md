# 2026-11-14 后端崩溃分析

本次检查用户提供的日志、安装目录批处理日志、只读任务快照、Windows 应用程序错误和资源耗尽事件，并读取原照片尺寸头信息。没有重新执行批量解码、识别或改动处理参数。

## 已确认的事实

1. 18:06:49、18:11:03 两次 Windows Application Error 1000 都指向安装版 `toolkit/python.exe`，故障模块为 `cv2/cv2.pyd`，异常 `0xc0000005`，相同模块偏移 `0x1b8d930`。界面记录的退出码 `-1073741819` 即该异常的有符号表示。这是原生代码访问冲突，通常的 Python `try/except` 无法保住进程。
2. 18:11:03 同时出现 Windows System 2004 资源耗尽事件，记录编号 324781。事件内 Python PID=55500（0xD8CC），与本次应用错误的进程编号一致，启动时间也对应 18:09:36 的后端。
3. 当时系统提交内存为 145,566,076,928 / 145,626,202,112 字节，即 135.569 / 135.625 GiB，仅剩约 57.34 MiB 提交额度。后端自身提交内存为 45,796,483,072 字节，约 42.651 GiB。这里的提交内存不能等同于进程当时驻留在物理 RAM 中的大小。
4. 系统物理内存约 47.656 GiB，当时使用率约 95.72%；系统配置为自动管理分页文件。因此证据不支持“只是没有开启分页文件”，也不能仅靠界面上 GPU 显存大小解释该崩溃。
5. 同一时刻，其他两个应用也记录了崩溃，进一步支持系统级内存压力，而不是只发生在 Neri 的普通 Python 异常。

Windows 事件证据保存在 `runs/backend_crash_analysis_20261114/application_events.json` 和 `resource_exhaustion_event.xml`。原生转储仍在用户的 `AppData/Local/CrashDumps/python.exe.55500.dmp`，另一次为 `python.exe.476.dmp`。

## 发生阶段

两次均处理 `HH009` 的 5,187 张照片，使用实验分类模型、自动批量、增强和 FP16 探测设置。日志显示自动选择每批 32 张。

- 第一轮最后保存第 2 批，约 64 张。
- 第二轮最后保存第 4 批；只读任务快照确认 `processed=128, total=5187`。
- 均未出现 `DINOv3 finalization starting`，还未进入完整序列汇总及其后的 HDBSCAN 聚类。

因此，本次崩溃的执行阶段属于照片批量检测、分类与并行预读，不能归因于已经运行的 HDBSCAN 拟合。`half is deprecated` 是重复出现的弃用警告，前面的多个批次在该警告之后正常完成；它不是这里记录的原生致命异常。

## 主内存压力的明确来源

按第二轮任务实际文件顺序抽查前 256 张的图片头：241 张为 9248×5200，15 张为 2704×1520。前者约为 4,809 万像素；JPEG 文件大小不能代表解码后的大小。

当前安装代码与仓库相应处理代码哈希一致：

- `system/image_processor_legacy.py:268` 用 OpenCV 按原分辨率读入 BGR 图；第 274 行另生成完整 RGB 副本。预读批内最多使用 8 个解码线程。
- `system/backend/inference_batching.py:26` 允许预读队列中最多 3 个批次。它按批次数限制，而非按解码字节数限制；当前批与前后批交接时也会有额外引用。
- `system/backend/inference_batching.py:57` 自动批量依据 GPU 可用显存和检测输入 `imgsz` 估算，没有按原图像素数、主内存及系统提交额度约束预读量。
- 分类裁剪与补边还会产生临时数组，模型和运行库也需要内存。

仅 BGR、RGB 两份 uint8 数组的静态估算：

|范围|大小|
|---|---:|
|1 张 9248×5200 图片|275.17 MiB|
|32 张同尺寸图片|8.599 GiB|
|3 个同尺寸批次|25.797 GiB|
|4 个同尺寸批次的交接范围|34.396 GiB|
|任务实际前 128 张，含小尺寸图片|30.710 GiB|

这些是按像素数计算的容量，不是对崩溃瞬间各 Python 对象的实测；不能据此断言全部 42.651 GiB 的具体分配。它已说明当前“显存允许就批量 32 + 按批数预读 + 全尺寸双色副本”的策略不适合这批高分辨率照片。

## 结论和处理方向

已确认的直接故障是 OpenCV 原生访问冲突；同 PID、同时刻的系统提交内存耗尽是最强的触发原因证据。全尺寸解码及预读策略是代码中明确存在的主要内存压力来源。尚未通过带符号的原生栈确认 OpenCV 内究竟是哪一次 `imread`、色彩转换或补边调用失效，也不能仅凭本次记录认定存在长期内存泄漏。

临时缓解：把批量从自动改为固定 4，观察稳定性；内存仍紧张时降为 1 或 2。批量 4 的同尺寸 BGR/RGB 基础容量约 1.075 GiB/批，明显低于批量 32，但它不是对总峰值的保证。当前 FP16 选项已开启，不能消除 CPU 上的全分辨率 uint8 图片副本。

软件修复重点：按照片尺寸及剩余提交额度限制批量与预读字节数；减少并发大图解码；按需转换 RGB；及时释放原图及裁剪临时对象；在进入解码前检查内存余量。单纯捕获 Python 异常或在原生访问冲突之后重试，不能防止后端进程退出。
