# 自动 batch 的主内存保护

针对 2026-11-14 的 4800 万像素照片崩溃，照片批量现在同时受 GPU 上限、原图像素数、可用物理内存及 Windows 剩余提交额度约束。改动位于 `codex/hdbscan-rejection-clusters` 分支。

## 解码前决定批量

`system/host_memory.py` 仅通过 Pillow 图片头读取宽高，不为估算分配整张图片。每张按至少 12 字节/像素估算工作内存，涵盖 BGR/RGB 两份 uint8 图片及部分解码、裁剪临时空间。解码后还会根据实际数组字节数上调估算，避免仅依赖图片头。

Windows 使用 `GlobalMemoryStatusEx` 读取物理内存和 `ullAvailPageFile`；后者是当前进程还能提交的内存额度，不是磁盘剩余容量。[Microsoft 定义](https://learn.microsoft.com/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)

安全预算取以下约束的最小值：

- 全部在途照片的估算池不超过总 RAM 的 15%，且最多 8 GiB。
- 可用物理内存扣除 512 MiB～2 GiB 预留后，只使用剩余量的一半。
- Windows 提交额度扣除 512 MiB～2 GiB 预留后，只使用剩余量的一半。

内存查询不可用时采用 1 GiB 保守池；无法读取图片头时单张尝试，超过 Pillow 安全像素上限的图片不绕过检查。单张也无法满足预算时，在原生解码前以清晰的内存不足错误停止任务，而不是强行处理。

GPU 吞吐量与显存调优继续作为批量上限。实际照片批量可以更小，也可以随分辨率和内存余量变化；用户保存的“自动”设置不被改成固定数字。手动批量也不能绕过照片内存保护，其数值作为上限。

## 限制预读和释放引用

原来可预读多个完整批次，现在只保留当前批及最多一个后续批。两者共同受估算池约束。排队批次在真正解码时再次检查内存，不满足预算就缩小重试。大图会减少解码线程数；主线程在等待预读时仍检查取消请求。

每批检测结果保存后，释放预读 Future、图片数组及 Ultralytics predictor 持有的上批原图引用，模型权重继续保留。发生可捕获的 CPU 分配异常时，自动 batch 会减半；不会把内存分配失败静默当成无动物或坏图。单张仍失败时保留已经完成的任务进度，提示释放内存后继续。

这是一套基于估算和实时余量的保护，不能保证任意原生库、异常文件或其他进程突然抢占内存时绝不崩溃。完整序列汇总、未知拒识阈值、HDBSCAN、编码器精度及图像预处理规则不随本改动改变。

## 验证

测试覆盖 4800 万像素图片头、小图继续使用大 batch、提交额度仅剩 57 MiB 时拒绝调用解码器、混合尺寸、不丢图不乱序、取消、CPU 分配失败减半、解码数组生命周期、模型缓存释放，以及任务失败后保留进度并继续处理。

相关回归测试共 133 项通过。使用已安装的真实探测模型在 CPU 上连续调用两次，并在两次之间清理 predictor 的原图引用，第二次调用正常完成，验证了缓存清理不会卸载或破坏模型。

对原问题文件夹的前 256 张照片只读取图片头，在当时可用内存条件下，请求上限 32 被规划为主要每批 8 张；混合小图的批次为 11～14 张，最后不足一批为 1 张。这只是当时内存状态下的规划，不是固定限制。

另使用一张字节相同的本地副本验证真实 OpenCV 解码：9248×5200，BGR/RGB 数组合计 275.17 MiB。进程私有内存在解码前约 1404 MiB，解码后约 1689 MiB，释放后约 1412 MiB。该读数不是完整模型处理峰值；没有重跑全部 5187 张大图。

本次独立解码验证使用 ASCII 工作区副本，因为隔离进程直接读取原中文路径时 OpenCV 返回了读取失败；未修改原照片。实际部署后的整批稳定性仍需通过用户任务观察。
