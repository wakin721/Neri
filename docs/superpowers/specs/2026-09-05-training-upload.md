# Neri consent and training uploads

Approved user request: first-use agreement; separately opt in to background photo compression and annotation uploads while marking. Each physical source folder contributes at most three confirmed empty photos, persisted across restarts. Confirmed species photos are uploaded and categorized by every assigned species. Destination is OneDrive/NeriCloud/Neri_Data/Training (OpenList /Neri_Data/Training).

Operator: 和錦わきん. Privacy contact: wakin721@outlook.com. Agreement version: 2026-09-05. The supplied draft is source material, updated for explicit automatic submission and Microsoft global storage. Do not promise irreversible anonymity: strip metadata/paths and exclude known person/vehicle labels; visual identities/watermarks require user screening. Photos only, no video or library scans. Nothing uploads before explicit separate opt-in; declining has no effect on core functions. Withdrawal cancels pending/in-flight work before the next transfer; completed submissions are not silently deleted.

Architecture: Flutter consent/settings UI calls the local Python privacy API. A dedicated SQLite journal under the user's local application data keeps consent, per-source identities, reservations and retry state (outside disposable temp/cache). Annotation persistence only enqueues lightweight work. One daemon worker debounces for ten seconds, compresses JPEG to max long edge 2048 / quality 82, strips metadata, creates allowlisted JSON, and uses a cloud broker for short-lived OneDrive upload sessions. Do not alter local source images. Compressed bounding boxes must stay consistent with stored pixel orientation; machine boxes are explicitly marked as model predictions, not relabeled as human-verified boxes.

Local API: GET /api/privacy -> {agreement_version, agreement_accepted, participation_decided, training_enabled, stats:{pending,uploading,uploaded,failed,skipped}}. PUT /api/privacy body {agreement_version:'2026-09-05',training_enabled:bool} persists acceptance and explicit choice. DELETE /api/privacy/queue discards waiting jobs while retaining completed empty-photo quota/history. Both mutations return the status object. Generic settings cannot set consent.

Cloud base: https://myneri.top/api/training. POST /v1/submissions body {sample_id:32 hex, revision:positive int, secret:per-sample random token, species:list of labels, image_bytes:int, annotation_bytes:int}. Empty category is 空照片. Response {sample_id,revision,targets:[{kind:'image'|'annotation',species,upload_url,cancel_url,chunk_size}]}. Completed retries return already_complete:true and targets:[]; clients validate sample ID/revision before accepting that receipt. POST /v1/submissions/{sample_id}/complete body {revision,secret} verifies both files and their sizes, then replaces older revisions/categories. DELETE /v1/submissions/{sample_id} body {secret} deletes only that owned submission. DELETE on a cancellation capability removes the incomplete attempt and any finished partial files. Broker uses a server-owned fixed destination, validates labels/lengths and declared sizes, and persists ownership/idempotency. No master credential reaches the desktop. Upload URLs are bearer capabilities; never log them. No authorization header on OneDrive PUTs.

Remote storage: Training/{species}/{sample_id}-r{revision}-{random_attempt}.jpg and matching .json. Every species receives the pair; JSON contains all labels. Path-unsafe labels and case-folding/Unicode-normalization collisions within one sample are rejected. Each attempt gets new recorded paths to avoid OpenList's automatic rename-on-conflict. Subsequent label changes use a new revision; previous files are removed only once new files are complete. Pending updates coalesce. Undo to unverified removes pending work and queues removal of prior uploaded data. Existing unrelated data/services remain intact. Training folder access is restricted to administrator IDs, including every existing descendant metadata record, without changing sibling folders.

User clarification: videos are excluded; photos and JSON must travel directly from the desktop to OneDrive because server bandwidth is limited. The server handles only small control requests. The public API has no photo relay route. OpenList's session file_size is not an enforced Microsoft ceiling: daily byte budgets limit declared sizes; completion checks actual sizes and removes mismatches. This does not prevent temporary excess storage from a modified client before verification/cleanup. This direct-mode operational limit is documented instead of promising a hard remote byte ceiling. Incomplete attempts are revoked and removed after 20 minutes, on five-minute sweeps; completed revisions expire after 365 days. Failed cleanup stays journaled and retries. An interprocess OS lock protects broker operations across explicit commits; the desktop uses physical file/directory IDs, atomic SQLite reservations and a separate interprocess worker lock.
